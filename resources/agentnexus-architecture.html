AgentNexus: One Rack for a Fleet of Plants

How AgentNexus runs thousands of AI agents across every plant, serves and improves the models they use, and works with the AgentMesh pod at each site — without ever controlling equipment.

Unovie.AI · Physical AI for deep-tech industries Revision 1.0 · November 2026 Hardware: AMD Ryzen AI Max+ 395 reference rack · NVIDIA DGX Spark

Abstract

AgentNexus is a single rack of small servers in a central cabinet. It runs thousands of software agents in sealed sandboxes, serves the language model those agents use, and improves that model over time with small, tested add-ons. It works alongside the AgentMesh pods at each plant, which keep the fast loop next to the machines; AgentNexus works at business speed across all of them and never moves plant equipment. Numbers marked "estimate" have not been measured yet.

1The short version

AgentMesh pods sit next to the machines at each plant and react within milliseconds. Some work doesn't need to be that fast but needs more room: agents that look across several plants, write reports, check work orders, or wait for days for a person to reply. AgentNexus is where that work runs. It answers within about half a second.

CPUs

Run the agents

Every agent runs in its own sealed sandbox. Agents that are idle are saved to disk and put to sleep, then woken when someone needs them. That lets one rack hold far more agents than it could keep running at once.

GPUs

Serve and improve models

One open-weight model, the Unovie Reasoning Model, answers every request. Small add-ons (adapters) specialise it for particular jobs; they're trained on the rack itself, tested, and switched on without restarting anything. A small companion model, the Unovie embedding model, handles search.

Platform

Keep it running

One cluster runs everything. Data is copied so that losing a server, or a whole shelf of four servers, doesn't lose work that was saved. The core runs on its own; only the business skills (section 10) call out, to Claude and your ERP.

2Where it fits

Plants keep their own AgentMesh pods. AgentNexus sits above them in a central cabinet and talks to them over encrypted links. It sends finished results, such as work orders, to business systems. It never sends commands to plant equipment.

Unlike the AgentMesh pods, which stay air-gapped at the plant, AgentNexus can also connect out: its business skills (section 10) draft quotes, quality reports and the morning production report using Claude, Anthropic's language model, and read the customer's ERP and document systems. Those calls go out only, and nothing is sent to a customer or supplier until a named person approves it.

3How it's organised

The rack is split by kind of chip. The processors (CPUs) run agents. The graphics processors (GPUs) do model work. Every server has both, so every server takes part in both. A shared platform underneath keeps them running.

Which models it uses

The rack standardises on two open models from Google, plus the router project's decision models, so that everything is trained, tested and served the same way. Using another model is a deliberate, recorded decision.

Answering requests (agents, chat, tools)Unovie Reasoning Model (open weights)A compressed copy on 24 GPUs for speed; the full-precision copy on 12 GPUs, where adapters can be applied. Already proven on the AgentMesh servers.

4What happens, step by step

A. An agent asks a model. The agent sends its request to one address. The router reads it, asks a small decision model which option fits, and sends it to the Unovie Reasoning Model: the compressed copy for general work, or the full copy with a specialised adapter. Only work that needs an external model, such as a business skill that calls Claude, is sent out through the exit gate. The router's own work is meant to take under a tenth of a second.

B. A plant talks to an agent. Most agents are asleep most of the time, saved to storage. When a request arrives, the agent is loaded onto any free server and woken. The target for waking is under half a second; we haven't measured it on our hardware yet.

C. A model gets better. Once a week for each adapter, if enough new results have come in, a training job starts on one of the 12 training servers. The Kiln asks the model to attempt tasks, has the attempts scored by test environments and larger decision models, and adjusts the adapter. The new adapter is then tested on cases it has never seen, tried quietly on a small share of real requests, and switched on only if it does better than the current one. The scoring code runs in the same sealed sandboxes as the agents.

5The hardware

Every server is the same small machine already used in AgentMesh. Four of them sit on one shelf (three rack units). Twelve shelves fill the rack. Using one model of server everywhere means one spare-parts kit and one software image, and any server can take over from any other.

Why the decision models don't use the AI accelerator (NPU). Every server has one, and it passes AMD's own test at 51 TOPS. But a model only runs on it after being converted with AMD's tools, and those tools can't yet handle the design of our decision models or the reasoning model. The tools that do run language models on this NPU on Linux only offer a fixed list of models, which doesn't include the base the decision models are built on. Smaller, simpler helper models (the kind that sort alarm texts or classify requests) look like a good fit, so we'll test one on the NPU and move them there if it's as fast and accurate as the graphics chip. That would free graphics time for the main model.
The memory is shared between the processor and the graphics chip. A large model loaded on the GPU leaves less room for agents on the same server, so memory is the resource we plan around most carefully.

The limit is model speed, not agent count. If every awake agent asked the large model a question at the same moment, each would get its answer slowly. The real number of agents the rack can support depends on how busy they are, and we'll measure it with real workloads.

Apart from three small pieces of our own (the job that switches adapters on, the service that starts training jobs, and the link between the router and the decision model), everything new is open source. The rack runs without internet access: software, models and updates are brought in and checked before use. The one exception is the business-skills layer (section 10), which needs an outbound link to Claude and the customer's ERP, and is simply switched off at sites without one.

10Business skills: Claude and your ERP

Much of a plant's day is paperwork built from records: pricing a new job, writing up a failed inspection, working out why a machine stopped, asking suppliers for quotes, and assembling the morning production report. Anthropic publishes a set of 17 ready-made skills for this work, Claude for Manufacturing, as open source. They were written for exports that land once a night. AgentNexus can run them on the plant's own live, time-stamped records from AgentMesh, so a breakdown write-up can be waiting when the technician arrives, not the next morning.

The router decides what goes out. The Unovie Model Router is the single integration point between agents and every model, local or external. It keeps private decisions and routine work, such as classifying an event, checking a figure or drafting from a template, on the rack's own models, and sends only the work that needs Claude out through the exit gate. Each external call is a metered cost and a copy of data leaving the building, so routing locally first keeps the running cost of external models down and keeps private decisions private.

Commissioning by interview. The same layer can set up a new AgentMesh pod. Claude interviews the site engineer about the hardware and drafts a reference file for every asset and output, plus the site's output map. The customer's controls engineer and Unovie review every lane and limit, and the result goes to the pod as a signed site-config release, the same way software images and models do. AgentNexus never opens a live connection into the pod, and nothing reaches it unreviewed.

How it connects. Each skill runs as an ordinary agent (flow B) with a few new services around it: one that serves plant data in the shape the skills expect, a store for the plant's settings and the two dashboards, an approvals inbox, and a scheduler. The business systems are reached outbound and read only: Oracle NetSuite or Infor M3 for orders and costs, Microsoft 365 for documents. Autodesk Fusion stays on the engineer's own computer, because it only accepts connections from that machine.

In design. This layer is designed, not yet built. Only AgentNexus connects out; the AgentMesh pods stay air-gapped. The layer needs an outbound link to Claude, so it is switched off at sites with no internet, and controlled data (export-controlled or CUI) never leaves the rack: on controlled defense programs the skills stay off.

11Glossary

Agent
A program that works on a task on its own, using models and tools, sometimes over hours or days.
Adapter (LoRA)
A small add-on to a language model that changes its behaviour for a specific job, without retraining the whole model.
AgentMesh
Unovie's pod at each plant. It reacts to equipment signals within milliseconds.
Claude
Anthropic's language model, reached over the internet. AgentNexus uses it only for the business skills (section 10), and the router sends it only the work the local models shouldn't handle; the AgentMesh pods never call it.
CPU / GPU
The general-purpose processor, and the graphics processor used for model work.
Decision model
A model that answers fixed, typed questions with a probability for each possible answer, instead of writing free text. Fast and easy to check.
Embedding
A list of numbers that stands for the meaning of a piece of text, so that similar texts can be found quickly.
Unovie Reasoning Model
The language model behind every answer: an open-weight model small enough to run on one of our servers.
Cluster
Software that runs and restarts programs across many servers as if they were one system.
NPU
A separate AI accelerator built into the processor. Efficient for small, fixed models, but each model has to be converted for it first.
Sandbox
A sealed space an agent runs in, so it can't reach anything it hasn't been allowed to.
Shelf (pod)
Four servers in three rack units, wired to each other. The unit we build, replace and plan failures around.
Training (reinforcement learning)
Improving a model by letting it try tasks, scoring the results, and nudging it toward the better attempts.
